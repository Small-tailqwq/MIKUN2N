# Runtime Change: 0.4.9 — Windows TAP setup and diagnostics

Version: 0.4.9

> [English](0.4.9.md) | [简体中文](0.4.9.zh.md)

## Problem

Driver registry conventions, adapter resets, initialization order and pipe buffering affect Windows setup reliability and evidence.

## Recorded changes

<a id="patch-12"></a>
### Patch 12

0.4.9 fixes configured MAC addresses being completely ineffective with the standard TAP driver. Upstream wrote only the nonstandard registry value MAC, while OpenVPN's official tap-windows driver reads the standard NDIS value NetworkAddress. The configured MAC was silently ignored and edge always registered with the adapter's built-in MAC. Write both values. Observed verification: the configured MAC failed before the fix and worked afterward; a quick reconnect with a fixed MAC rejected by the supernode could then recover immediately by selecting a random MAC.

<a id="patch-13"></a>
### Patch 13

0.4.9 skips the entire adapter disable/enable cycle when the registry MAC already matches the target, avoiding repeated adapter and Windows network-location resets. Do not select adapters with empty connection names. If reopening fails, retry enabling once rather than leaving the adapter disabled.

<a id="patch-14"></a>
### Patch 14

0.4.9 makes stdout unbuffered. When edge runs as a child process, stdout is a pipe and defaults to full buffering; an abnormal process exit could lose all adapter-configuration diagnostics.

<a id="patch-15"></a>
### Patch 15

0.4.9 applies TAP_IOCTL_SET_MEDIA_STATUS before configuring the IP address, so netsh and GetAdaptersInfo see an adapter that is already ready.
