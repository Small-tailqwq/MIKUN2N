# Runtime Change: 0.5.0 — Match relay policy by IPv4 and MAC

Version: 0.5.0

> [English](0.5.0.md) | [简体中文](0.5.0.zh.md)

## Problem

Peers learned from DATA can lack a virtual IPv4 address, leaving forced relay applied on only one side.

## Recorded changes

<a id="patch-16"></a>
### Patch 16

0.5.0 fixes manual pSp silently failing at one endpoint. n3n learned the peer's virtual IPv4 only from REGISTER; an entry first created by PACKET retained dev_addr=0. Applying forced relay by IPv4 matched zero entries, leaving local P2P and remote pSp, with latency jumping between two values. Three changes address this: set_peer_relay accepts an optional third MAC parameter and stores/matches policy by both IPv4 and MAC; any packet carrying dev_addr teaches it to an existing entry; recreating an entry after a socket change preserves dev_addr. Observed verification: applying a wrong IPv4 with the correct MAC matched zero entries before and one afterward, with forced_relay reflected in get_edges.
