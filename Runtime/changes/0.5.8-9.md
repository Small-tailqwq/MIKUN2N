# Runtime Change: 0.5.8-9 — NAT probing, assisted-path evidence and interface recovery

Version: 0.5.8-9

> [English](0.5.8-9.md) | [简体中文](0.5.8-9.zh.md)

## Problem

Probe-induced rebinding misclassifies cone peers; aggregate counters cannot locate assisted timeouts; stale interface preference prevents IPv6 recovery.

## Recorded changes

<a id="patch-53"></a>
### Patch 53

0.5.8-9: Stop the NAT probe from corrupting its own result, and keep cone
peers on a coordinated path. The probe asked observer A to send XREPLY from
port B to the data socket's mapping before that socket had contacted B. A
router that answers such a packet itself (ICMP port unreachable) then gave
the socket's later B flow a new public port: every A/B sample differed, so
cone NATs whose worker sockets calibrated as CONE, and whose A port equalled
the supernode's view, were reported as NAT4 eim=0/5. On one such router the
replies to the new B port never arrived (the observer answered every request,
confirmed by a capture on the server), the probe stayed "unknown", no NAT
summary was sent, and both peers fell back to uncoordinated local roles: six
rounds overlapped once, for about two seconds, before both sides stopped.
The filtering test now runs on a throwaway socket; the data socket only ever
sends PROBE to A and B. The supernode's REGISTER_SUPER_ACK view of the data
socket is kept as a third sample: if B stays silent for 4 s, A against that
port decides (reported as one sample, which supernodes accept), so planning
no longer depends on B. Cone<->NAT4 pairs now alternate calibrated worker
banks and the layered sweep per failed round, starting with banks, which is
the only way those misreported cone peers had reached NAT4 peers; one missed
bank coordination falls back to the sweep in the same round. An anchor facing
a layered cone peer ends with that peer's sweep, so retries stay aligned.
get_nat adds observed_port_sn and partial. Supernodes need this release to
plan cone<->NAT4 bank rounds; older ones make those rounds fall back after one
coordination timeout. Wire format and IPv6 generation 3 are unchanged.
tools/tests-nat.c covers the verdicts and that both ends and the supernode
agree on every round; live pairing is not yet verified.
Also fixes an upstream sock_to_cstr bug that passed inet_ntop a length larger
than its buffer. glibc's fortified inet_ntop aborts on that, so the Linux
supernode built from 0.5.8-2 or later source died ("buffer overflow detected")
as soon as it formatted an IPv6 socket, 38 s after start on a live server.
Windows builds were never affected: their actual output always fit.

<a id="patch-54"></a>
### Patch 54

(0.5.8-9) Assisted Minecraft traffic could time out while small probes stayed
responsive. The incident's global counters showed 3,039 fragments received
but only 1,310 reassemblies; that discrepancy cannot establish packet loss
or slot exhaustion. Add cumulative per-circuit/direction DATA and separate
heartbeat counts from submission through envelope checks and TAP writes,
plus per-outer-peer IPv6 submission and reassembly rejection counters.
Ordinary logs now retain bounded summaries and lifecycle/reset snapshots;
get_peer_assists exposes the directional counters for diagnostic recording.
Slot-full, expiry/missing bytes, duplicate/conflict and replay-window counts
distinguish local reassembly pressure from a missing receive stage. A
successful UDP submission still does not prove delivery. Four slots, the
two-second expiry, wire formats and transport selection remain unchanged.
This is instrumentation for the next three-host reproduction, not a claim
that the historical timeout's cause has been identified or fixed.

The 2026-10-11 review correction explicitly converts `checked_bytes` and `wire`
to `unsigned` for their `%u` log fields. The diagnostic values and transport
behavior stay the same. The [assistance contract](../../docs/PEER-ASSIST.md)
also clarifies that management queries require local assistance circuits;
successful and failed snapshots use the same state-change/periodic recording
rule and the session's diagnostic recorder. The Windows native rebuild and
existing `tests-ipv6` and `tests-wire` checks passed. No live connection or
runtime log-format reproduction was performed for this correction.

<a id="patch-55"></a>
### Patch 55

(0.5.8-9) Recover IPv6 selection when an old interface still reports a
preferred address but its router/upstream no longer works. Reconnecting
previously selected the same low-metric address even after another Wi-Fi
interface became available. Keep a working binding; sustained failures of
existing STUN/base-peer checks allow another interface to be tried, with a
30-second startup allowance and a 60-second failed-interface cooldown.
Large-probe loss, temporary queue pressure and idle/incompatible peers do
not trigger rotation. A new socket must bind before retiring the old one;
enumeration or replacement failures do not discard an existing binding.
Rebinding renews IPv6 path proof and candidate queries while retaining IPv4.
Normal logs identify the interface, address and reason. This does not add
concurrent paths, change generation 3, or require a supernode upgrade.
The earlier incident has no retained reproduction establishing its exact
cause; real router-failure and Wi-Fi recovery are not yet verified.
