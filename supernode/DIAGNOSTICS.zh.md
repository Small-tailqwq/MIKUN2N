# 可选的测试诊断

> [English](DIAGNOSTICS.md) | [简体中文](DIAGNOSTICS.zh.md)

私有测试版每次手动连接时，默认采用 **每次询问**。玩家点拒绝、按 Esc 或直接关掉对话框，日志都只留在本机。单次同意只对这一次连接（以及期间 edge 的自动重启）有效，不会被记成长期同意。设置里另有 **始终允许**（需要玩家在充分知情后再单独确认一次）和 **始终拒绝**（不弹窗、不上传）两个选项。长期授权与当前选中节点的身份和配置、具体的 HTTPS 接收地址以及固定的证书绑定在一起。编辑或切换当前节点都会让它失效，即使之后再切回来也一样；接收地址或证书变了，也要重新授权。私有测试配置绝不会预先替玩家打开长期授权。切换到「询问」或「拒绝」会立即撤销正在进行的长期上传。IPv4 和 IPv6 会话（包括连接失败的尝试）都遵循这套规则。

在主窗口里就可以停止上传，或者恢复诊断记录和上传，不需要重启客户端、edge 或断开连接。恢复时按当前选择的授权方式处理，并开始记录一个新的分段；被拒绝或撤销期间的记录永远不会补传。每次连接在本机最多保留四个 64 MiB 的分段（共 256 MiB），写满后覆盖最旧的分段。存储出错时会暂停记录，并在界面上给出恢复操作。接收端暂时不可用时，会在上述容量范围内重试；没能确认送达就被覆盖掉的分段，会显示为"未完整送达"。断开连接或退出程序时，最多再花八秒尝试把剩余内容传完。之后的连接绝不会上传更早的日志文件。

如果分段被接收端以 409（序号或内容冲突）或 410（已过期）拒绝，客户端会立即放弃上传这个分段；为防止每个新分段都被拒而导致频繁切换分段，会先退避三秒。每次收到 507（容量不足）时，客户端等待 30 秒，并保留同一个内容不变的待传分块以便重试。507 本身不会导致放弃或切换分段；不过等待期间，常规的本地容量轮换仍可能淘汰旧的积压内容。服务器腾出容量后，会自动继续上传。手动恢复会取消等待，并在重新取得（或仍然有效）的授权下开始一个新分段，同样遵守"恢复之前的记录绝不补传"的规则。遇到其他网络故障时，会保留这个内容不变的分块，在正常的滚动容量范围内做幂等重试。较新的分段可以继续上传；如果当前分段被拒，客户端会另起一个新分段。本机文件仍按原有的容量和保留期限管理。`upload_segment_abandoned` 会记录分段编号、HTTP 状态码和未确认的字节数，界面也会把这次上传标记为未完整送达。这些状态变化都不会改动授权，撤销授权后也绝不会重新开始上传。计入"放弃"的字节不会再重复计入后面的"超出容量丢弃"总数，两项统计互不重叠。`upload_capacity_wait` 会注明被保留的分段、分块和重试间隔。

接收端记录已过期 ID 的集合只存在内存里。接收端重启后，对一个已被清理的分段重试非首个分块，可能得到 409 而不是 410；现在这两种状态码在客户端走同一条恢复流程。这项修复不需要更新服务端，也不需要服务端额外保存状态。

记录的内容包括：UTC 时间、单调递增的时间偏移、批次/会话/事件标识、客户端构建和 edge 的哈希、网卡地址、NAT 检测结果、各对端的传输方式和延迟、连接状态变化以及 edge 原始的诊断事件。IPv6 诊断会记录地址选择、候选刷新、探测发送与对应 PONG 的 RTT、过期、发送失败、各类拒绝计数和流量总量。这些记录不会采集数据包内容、密钥、密码、无关文件或历史日志。已知的会话凭据和本机用户目录路径会在诊断字符串字段中脱敏。但记录里仍包含个人的网络信息和昵称；授权对话框会向玩家说明这一范围。

当前客户端使用第 3 代 IPv6 协议，按方向分别发现尺寸，并做有上限的隧道内分片，详见 [IPv6 传输](../docs/IPV6-TRANSPORT.zh.md)。`pong_matched` 报告已验证的字节数、对端的接收有效期和 `data_ready`；`data_path_ready` 表示开始用 IPv6 传数据包。`data_fragmented` 以及定期输出的分片/重组计数，用来区分"大包被分片发送"和"真的退回了 IPv4"。`version_mismatch` 表示对方是第 1、2 代客户端，继续走 IPv4。`peer_readiness_expired`、路径过期和套接字硬故障记录的才是真正的回退。扫描暂停和恢复事件，用来解释 IPv6 稳定期间 IPv4 打洞计数为什么停止增长。supernode 不需要修改协议；只需要双方客户端都是第 3 代。

私有测试会话会记录 `MikuN2N latency` 事件，内容包括单播探测的发送、ACK、十秒超时、ICMP 结果、过期样本和线路变化。借助节点、探测和批次编号等字段就能把结果对应起来，不需要记录数据包内容。现有的两秒探测间隔决定了这类日志的常规频率，会话日志的总量限制依然有效。线路一变，上一轮尚未完成的测量就作废。显示「暂无法测量」时重试并不会停止，也不代表好友已经离线。原生 PONG 的 RTT 与应用层测得的隧道 RTT 分开统计。

## 接收端

在 supernode 上复制本目录，然后以 root 身份运行：

```sh
bash install-diagnostics.sh --host YOUR_SERVER_HOST --batch ipv6-test-YOUR_BATCH
```

在主机防火墙和云服务商的安全组里都放行 TCP 5443。接收端使用专用的系统账户、本机生成的 TLS 证书和按批次单独生成的上传凭据；每个请求 128 KiB，按编号保存为 JSONL 分块，写入是原子的、可以安全重试；单个分段上限 64 MiB，总量滚动上限 2 GiB（超出时先删最旧的分段）。日志只能由管理员通过 SSH 查看，HTTP 服务不提供下载接口。分段在首次收到 24 小时后过期，服务启动时和之后每五分钟清理一次。对话框里仍写着"七天"的旧版客户端，同样按这个服务端策略处理。重新安装会更新配置中的保留期限字段，但不会更换凭据或证书。发布包内固定了服务器证书，用它来认证服务器，不需要全局关闭 TLS 校验。上传时禁用重定向和系统代理。证书有效期为 90 天。

把 `/etc/mikun2n-diagnostics/client.json` 直接拷进用于构建私有测试版的配置文件里；不要把它打印出来、提交到版本库，也不要放进公开的源码包。在其中添加一个 `Node` 对象，只包含 `Id`、`Name`、`Server` 和 `Community` 四个字段。绝不要把客户端保存的设置、玩家的 NodeId、记住的密钥、昵称或服务器私钥拷进去。这份配置里没有任何授权相关的设置。

```powershell
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:TestProfilePath="ABSOLUTE_PRIVATE_PROFILE_PATH" -o artifacts/private-ipv6-test
```

只有明确传入 `TestProfilePath` 时，才会把私有测试配置嵌入程序。测试版的设置保存在 `%LocalAppData%/MikuN2N/tests/<批次>/settings.json`；首次启动时会打开 IPv6，并预先添加选定的私有节点。常规版本已有的设置不受影响。诊断文件保存在 `%LocalAppData%/MikuN2N/logs/diagnostics-*.log`，按客户端本地的日志保留设置清理。不带这个属性的常规发布，没有任何内置节点或上传配置。

私有测试配置中可选的 `Ipv6StunHost` 用于地址发现，与日志上传互不相关。启动器在三秒的 DNS 超时内最多解析两个全局 IPv6 地址；edge 从它的对端套接字向 UDP 3478 发送标准的 STUN 绑定请求。观察者能看到的只有源地址和端口，以及一个随机的事务标识，看不到昵称、小组名称、会话令牌、应用数据或诊断日志。查到的候选地址仍由原来那台 supernode 通过 IPv4 交换，这台 supernode 也仍是唯一的诊断上传目标。诊断中会记录映射的查询、请求、应答和超时事件、本机 IPv6 网卡的 MTU、探测尺寸的变化，以及对每个对端已验证的 UDP 尺寸。日志上传的授权流程不变。

## 通过 SSH 查看双方客户端的日志

```sh
sudo python3 /opt/mikun2n/diagnostics/read-diagnostics.py /var/lib/mikun2n-diagnostics/YOUR_BATCH --sessions
sudo python3 /opt/mikun2n/diagnostics/read-diagnostics.py /var/lib/mikun2n-diagnostics/YOUR_BATCH --contains v6diag
sudo python3 /opt/mikun2n/diagnostics/read-diagnostics.py /var/lib/mikun2n-diagnostics/YOUR_BATCH --kind management_edges
sudo journalctl -u mikun2n-diagnostics.service --since today
```

每一行都带有固定不变的 `connection`、递增的 `segment` 和在整个连接内连续编号的 `sequence`。HTTP 层的 `session` 和所在目录对应一个分段。用 `--connection CONNECTION_ID` 可以把这次连接保留下来的所有分段合在一起看，包括恢复记录之后的部分。每个分段开头都会重复一份最基本的会话、连接和原生构建信息，方便对应。靠昵称、虚拟 IP 和对端 MAC，可以把两边的日志对上。两台客户端的时钟可能不一致：看服务器首次收到的时间用 `received.json`，看同一客户端内部的先后顺序用 `elapsedMs` 和 `sequence`。读取脚本按客户端的 UTC 时间合并两边的记录，但没法纠正没对准的时钟。

双方客户端必须各自独立同意。某一方的目录不存在，可能是拒绝了、停止了上传，或者连不上接收端；这不能证明对方客户端没有运行。界面提示"未完整送达"时，请保留本机的日志文件。要停止收集，停用 `mikun2n-diagnostics.service` 即可；删除已收到的日志或更换批次、凭据，需要管理员另行操作。
