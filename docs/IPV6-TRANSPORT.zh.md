# IPv6 传输，第 3 代

> [English](IPV6-TRANSPORT.md) | [简体中文](IPV6-TRANSPORT.zh.md)

0.5.8-4 测试版使用一个基于 [RFC 8899](https://www.rfc-editor.org/rfc/rfc8899.html) 原则的、有界的、两级的分组层发现方案。这不是一个完整的通用 DPLPMTUD 状态机。它把每个方向的已确认 UDP 尺寸与对端接收能力、路径存活以及更大的探测分离开来。

## 尺寸发现

- 基础 UDP 负载为 1232 字节（1280 减去 IPv6/UDP 头）。初始探测与 keepalive 使用该尺寸。传输启动前 `IPV6_DONTFRAG` 必须成功；探测不能静默地穿过 IP 分片。失败会禁用 IPv6 传输，并且即使没有详细诊断也会发出警告。Windows 测试版支持该 socket 选项；其他目标平台必须自行提供。
- 一个 47 字节的 PONG 确认精确的探测尺寸、challenge 与源端点、会话与线路代次。其较短的尺寸避免把反向的 MTU 强加给被测量的正向。可接受的最大响应年龄为 6500 ms。对端通告一个 1452 字节的接收上限。
- 基础路径检查通过后，edge 每十秒探测一个更大的尺寸：`min(1452, TAP MTU + 128, peer receive ceiling)`。在默认的 1290 字节 TAP MTU 下，这是 1418 字节。一个进来的小 PING 或一次成功的基础 PONG 永远不会抹掉之前已确认的更大的出站尺寸。
- 三个未应答的更大探测或一个本地的 message-too-large 错误会把分组化退回 1232 字节，并把下一次更大搜索推迟 60 秒。基础 keepalive 独立继续；可用的 IPv6 路径仍然有效。
- 两个端点都必须报告接收就绪后才会选择 DATA。真正的就绪/路径过期或硬 socket 故障仍走 IPv4 路径。暂时的本地队列压力是普通的 UDP 丢包，不会切换传输。
- 同一会话中变更的 rendezvous 候选会保留已检查的映射。过期会触发候选重新检查；新的会话 token 会清空所有路径证明。新选中的映射也会清空未完成的旧映射探测/重组。

这修复了观察到的 0.5.8-1 模式：一个进来的 1232 字节探测会撤销 1418 字节的证明，而 1383 字节的封装 DATA 反复落到 IPv4 中继。尺寸发现在 A 到 B 与 B 到 A 上是独立的；它们的上限可能不同。

## 隧道分片

超过已证明 UDP 上限的 DATA 会在 IPv6 隧道内拆分。每个分片使用现有的会话头，加上一个 64 位数据报 ID、16 位总长度和 16 位偏移（45 字节头）。重组先于普通 n3n 解码进行；内部的加密 n3n 字节保持不变。不记录任何应用负载。

edge 在来自已检查对端的第一个有效分片到来时为四个组装槽分配空间，每个受 n3n 包缓冲（2048 字节）约束，并有固定的两秒截止时间。会话重置或对端销毁时释放该分配；共享的对端结构只包含一个指针，因此 supernode 不分配任何组装缓冲。分配失败会发出限速警告。相同的重叠字节被忽略；冲突的重叠或总长度不一致会丢弃该组装。一个 1024 ID 的滑动位图会拒绝已完成/已过期/冲突的组装。窗口之外的旧 ID 即使在位图复用后仍被拒绝，只要分片持续到达；高速率无法重新打开重复投递。两秒内没有可接受的分片后，历史记录过期，从而与重建对端记录并重置其 ID 的旧发送方保持第 3 代兼容。延迟超过该空闲过期的重复包可以被投递，如同之前的两秒缓存。新发送方只对跨 edge 会话的分片数据报分配 ID，因此重建对端无法复用某个 ID，未分片的流量也不消耗任何 ID。一个已被接纳的组装即使在后来的 ID 推进窗口时也保持其最初的两秒截止时间。一个落在 1024 ID 窗口之外的第一个分片无法启动组装；该 ID 距离由源 edge 发往的所有对端共享。无效范围、未知会话、错误端点和过量的并发组装都会被拒绝。分片丢失会丢掉原始 UDP 数据报；没有可靠性/重传层。部分发送的数据报绝不会同时经 IPv4 重放。在独立分片丢失概率为 p 时，一个拆成两个分片的数据报以概率 (1-p)^2 成功；相关丢失会有所不同。因此分片会增加数据报丢失，而该传输有意不添加任何重传。

原生摘要暴露已发送/已接收的分片、完成的组装与瞬时丢弃。个别事件报告路径过期与发送错误。过时的 `oversize_fallback_*` 计数器在 0.5.8-3 中已移除；请检查分片计数与实际的路径/发送失败事件。

`get_edges` 保留 `ipv6_checked_udp_bytes`（已确认的出站 UDP 上限，未激活时为零）和 `ipv6_peer_rx_udp_bytes`（对端通告的接收上限）。冗余的 `ipv6_tx_udp_bytes` 别名和由代次推导的 `ipv6_fragmentation` 标志已移除。接收上限不是对反向路径的测量。反向出站上限从另一端点的行获取。这些字段面向本地 API 使用方和经同意的原始 `management_edges` 诊断记录；好友界面不显示它们。它们不会改变路由器的 IPv6 MTU 或对端的 TAP 设置。

## 兼容性与验证

两个客户端都需要第 3 代才能进行 IPv6 测试。第 1/2 代和普通 n2n 客户端保持 IPv4 兼容；仅构建号不匹配是允许的。现有 supernode 转发候选/身份，无需任何线路改动。到 supernode 的 IPv4 可达性仍是必需的。NAT66 发现在私有配置中保持启用。

相应原生源码中的 `tools/tests-ipv6.c` 拦截所有发送并检查不对称尺寸、丢包、乱序、重复、过期、受限缓冲、会话/端点拒绝和本地发送错误，而无需打开 socket。先构建原生源码树；`make` 现在会把该检查与 `tests-wire` 一起构建。运行这两个可执行文件。源码归档包含这两个检查。

客户端/接收端离线检查：

```powershell
dotnet run --project tools/offline-tests/OfflineTests.csproj -- "$env:TEMP/MikuN2N-offline-check"
python tools/offline-tests/test_server.py artifacts/offline-server
```

0.5.8-4 的检查还覆盖 1200 次不消耗 ID 的未分片发送、一个被接纳的组装在 ID 跳跃后存活到其截止时间、真实的 64 MiB 日志轮转、精确的上传字节/记录/分块序列、507 之后保留的分块，以及容量退避期间的手动恢复/撤销。它们并不确立真实的公网 IPv6/NAT66 行为、两套 WPF 主题、持续的游戏流量或云账单的减少。
