# IPv6 传输（第 3 代协议）

> [English](IPV6-TRANSPORT.md) | [简体中文](IPV6-TRANSPORT.zh.md)

0.5.8-4 测试版参照 [RFC 8899](https://www.rfc-editor.org/rfc/rfc8899.html) 的思路，实现了一套分两档、探测次数有上限的分组层 MTU 发现。它将每个方向上已确认的 UDP 尺寸、对端接收能力、路径存活状态和更大尺寸的探测分开处理。

## 本地地址选择与网卡切换恢复

edge 每十秒重新枚举本机 IPv6 地址。Windows 上最初按网卡已启用、存在 IPv6 网关、
地址处于首选状态且剩余寿命足够，再结合地址类型和接口 metric 选取候选。
选中的源地址绑定到一个 IPv6 socket，再通过 STUN 和好友探测判断是否保留该绑定。

只要当前绑定仍符合候选条件，且没有持续的探测失败，就保留它。通过校验的
STUN 回应或匹配的好友 PONG 会清空失败窗口。只有 STUN 请求超时/硬发送错误和
合格好友的基础探测失败参与判断；大尺寸 MTU 探测、临时队列错误、未配置观察者、
已知协议不兼容或离线的好友都不作为切网卡的依据。新绑定有 30 秒启动宽限期；
至少三次失败、失败持续 20 秒且最近 15 秒仍有失败时，才尝试另一接口。

重试时将失败的整块接口暂时避开 60 秒，避免在它的多个临时地址之间打转，
错过可用的 Wi-Fi 接口。最多记录 16 块近期失败的接口。当前地址若已经不在
合格候选中，可以直接选择替代，无需等待失败窗口。没有替代候选但原地址仍
符合条件时保留原绑定继续尝试恢复；没有本地候选时继续使用 IPv4。
地址枚举调用失败会保留当前绑定。替代 socket 必须先完成配置和绑定，才关闭
旧 socket；替代绑定失败也进入接口冷却。

重绑会清理旧的本地映射事务、对端路径/就绪证明、未完成探测与分片重组，随后
刷新对端候选，以新的本地会话令牌重新探测。IPv6 重新建立期间仍可使用 IPv4。
普通日志记录地址选择、接口和失败原因。替代地址可用后，即使原接口 metric 更低，
也不会每次刷新又切回去。用户在 Windows 中管理网络连接；恢复时选择另一块接口
上的一个地址，系统路由保持不变。

## 尺寸发现

- 基础 UDP 负载为 1232 字节（1280 减去 IPv6 和 UDP 头）。最初的探测和保活包都用这个尺寸。传输启动前必须成功设置 `IPV6_DONTFRAG`，确保探测包不会被 IP 层悄悄分片后蒙混过关。设置失败就停用 IPv6 传输，即使没开详细诊断也会给出警告。Windows 测试版支持这个套接字选项；其他平台必须自行提供。
- 对端用一个 47 字节的 PONG 应答，其中精确回带探测包的尺寸、挑战值、源端点、会话和协议代次。PONG 本身很小，这样测正向路径时不会被反向路径的 MTU 拖累。超过 6500 ms 的应答不予接受。各端对外通告的接收上限是 1452 字节。
- 基础路径确认后，edge 每十秒尝试一次更大的尺寸：`min(1452, TAP MTU + 128, 对端接收上限)`。默认 TAP MTU 为 1290 字节时，这个值是 1418 字节。收到对方发来的小 PING，或基础尺寸的 PONG 成功，都不会抹掉此前已确认的更大出站尺寸。
- 连续三次大尺寸探测没有应答，或本地报告报文过大，就把分组尺寸退回 1232 字节，并在 60 秒后才再次尝试更大尺寸。基础保活包照常发送，IPv6 路径仍然可用。
- 双方都报告已准备好接收之后，才开始用 IPv6 传数据包。真正的就绪状态过期、路径过期或套接字硬故障，仍会改走 IPv4 路径。本地发送队列暂时拥堵只算普通的 UDP 丢包，不会触发切换。
- 同一会话中汇合候选发生变化时，已经验证过的映射会保留。过期会触发重新检查候选；会话令牌换新则清空全部路径验证结果。选中新的映射时，也会清掉旧映射上尚未完成的探测和重组。

这修复了 0.5.8-1 中观察到的问题：对方发来的 1232 字节探测会推翻已验证的 1418 字节结果，导致封装后 1383 字节的数据包一再落回 IPv4 中继。A→B 和 B→A 两个方向的尺寸发现各自独立，上限可以不同。

## 隧道内分片

超过已验证 UDP 上限的数据包会在 IPv6 隧道内部拆分。每个分片沿用现有的会话头，再加上 64 位数据报 ID、16 位总长度和 16 位偏移（共 45 字节头）。先重组，再交给 n3n 做常规解码；内层已加密的 n3n 字节原样不动。日志里不记录任何应用数据。

edge 收到来自已验证对端的第一个有效分片时，才分配四个重组槽，每个槽不超过 n3n 包缓冲区的大小（2048 字节），截止时间固定为两秒。会话重置或对端记录销毁时释放这些内存；共享的对端结构里只放一个指针，所以 supernode 不会分配任何重组缓冲。分配失败会发出限频的警告。重叠部分字节相同时直接忽略；重叠内容冲突或总长度前后不一致，就丢弃这一组重组。一个覆盖 1024 个 ID 的滑动位图负责拒绝已完成、已过期或有冲突的重组。只要分片持续到达，落在窗口之外的旧 ID 即使在位图槽位被复用后也依然被拒绝，高速收包不会让重复投递再次发生。如果两秒内没有收到任何可接受的分片，历史记录就会过期；这是为了兼容会重建对端记录并把 ID 归零的旧版第 3 代发送方。因此，延迟超过这段空闲期才到达的重复包仍可能被投递，这和之前两秒缓存的行为相同。新版发送方在整个 edge 会话范围内分配 ID，而且只给需要分片的数据报分配，所以重建对端记录不会复用 ID，不分片的流量也不消耗 ID。已经接纳的重组，即使后来的 ID 推动了窗口，也仍按最初的两秒截止时间处理。第一个分片若落在 1024 个 ID 的窗口之外，就不能开启新的重组；这个 ID 距离是在源 edge 发往的所有对端之间共用的。范围无效、会话未知、端点不符以及超出并发上限的重组都会被拒绝。任何一个分片丢失，整个原始 UDP 数据报就丢失；这里没有可靠传输或重试层。发出了一部分的数据报，绝不会同时再经 IPv4 重发。若每个分片独立地以概率 p 丢失，拆成两片的数据报成功到达的概率是 (1-p)²；丢包彼此相关时结果会不同。

原生侧的汇总信息给出已发送和已接收的分片数、完成的重组数以及临时丢弃数。路径过期和发送错误作为单独事件报告。旧的 `oversize_fallback_*` 计数器已在 0.5.8-3 中删除；请看分片计数和实际发生的路径过期、发送失败事件。

`get_edges` 保留两个字段：`ipv6_checked_udp_bytes`（已确认的出站 UDP 上限，未启用时为 0）和 `ipv6_peer_rx_udp_bytes`（对端通告的接收上限）。多余的别名 `ipv6_tx_udp_bytes` 以及由协议代次推算出的 `ipv6_fragmentation` 标志已删除。接收上限并不是对反向路径的测量结果；反方向的出站上限要看另一端的那一行数据。这些字段供本机调用管理接口的程序，以及经用户同意上传的原始 `management_edges` 诊断记录使用；好友界面不显示它们。

## 兼容性与验证

两端客户端都必须支持第 3 代协议才能测试 IPv6。第 1、2 代以及普通 n2n 客户端仍可用 IPv4 互通；只是构建号不同是允许的。现有的 supernode 只负责转发候选和身份信息，不需要改协议。客户端仍然必须能通过 IPv4 访问 supernode。私有测试配置中仍开启 NAT66 发现。

对应原生源码里的 `tools/tests-ipv6.c` 会拦截所有发送操作，在不打开任何套接字的情况下，检查双向尺寸不对称、丢包、乱序、重复、过期、缓冲区上限、会话与端点校验以及本地发送错误。先构建原生源码树，`make` 现在会把这项检查和 `tests-wire` 一起编出来，然后两个程序都要运行。源码包里包含这两项检查。

客户端与接收端的离线检查：

```powershell
dotnet run --project tools/offline-tests/OfflineTests.csproj -- "$env:TEMP/MikuN2N-offline-check"
python tools/offline-tests/test_server.py artifacts/offline-server
```

0.5.8-4 的检查还覆盖了以下内容：连续 1200 次不分片的发送不消耗 ID；已接纳的重组在 ID 跳跃后仍能保留到截止时间；真实的 64 MiB 日志轮转；上传的字节数、记录序列和分块序列完全准确；收到 507 后分块被保留；以及容量退避期间手动恢复和撤销授权。

实机验证包括公网 IPv6/NAT66、路由器故障或 Wi-Fi 切换时的 Windows
网卡选择、两套 WPF 主题和持续游戏流量。切换网卡时需记录中断和恢复情况。

## 只读本机网络状态

基于 0.5.8-10 的本地维护构建在 `get_nat` 中增加可选字段：

| 字段 | 取值 |
| --- | --- |
| `ipv6_status` | `disabled`、`checking`、`unverified`、`available`、`unavailable` |
| `ipv6_address_kind` | `none`、`global`、`ula` |
| `ipv6_mapping` | `unknown`、`untranslated`、`port-translated`、`address-translated` |

既有 `ipv6_nat66_supported` 仅表示能力，不能证明当前网络存在地址转换。
可用状态需要 30 秒内成功的源地址绑定往返验证。映射类型还需要同一绑定套接字
收到有效的新鲜观察回复，再比较外部端点和本地端点。地址转换可能是 NAT66 或
NPTv6，当前观测无法进一步区分，也不证明任意主动传入连接或所有好友均可达。

读取这些字段不会探测或枚举网卡，客户端沿用既有四秒 NAT 查询，丢弃超过
12 秒的旧报告。响应不新增地址信息。旧运行时缺少字段时保持待验证或状态未报告，
不将其视为网络故障。
