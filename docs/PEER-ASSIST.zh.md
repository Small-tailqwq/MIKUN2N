# 好友协助转发

> [English](PEER-ASSIST.md) | [简体中文](PEER-ASSIST.zh.md)

0.5.8-8 的首版实现允许申请人 T 选择一位自愿协助的好友 R，转发 T 与指定好友 L
之间的双向单播数据。每一对 T/L 分别选择 R；R 可以分别接受多位好友的申请。

## 使用协助转发

在通信对象的好友右键菜单选择“选择协助转发…”。候选窗口打开期间会查询质量。
R 收到申请后出现待处理按钮，不弹模态窗口或抢焦点。关闭窗口会取消尚未完成的
对外申请，不会停止已经建立的会话。任一参与者均可结束协助。授权只在当前连接
有效，重连后不自动恢复授权。连接质量、申请与会话管理放在二级窗口；
主界面显示实际协助状态和待处理申请入口。

## 质量报告

新版客户端默认允许同组好友查询自己与指定好友的近期连接质量。报告按需单播，
由 T 在本地排序候选，沿用现有 supernode，无需升级服务端。

沿用两秒一次的 UDP hello/ack，在 60 秒窗口中记录已完成样本数、超时数、平均及
95 分位往返延迟、相邻成功 RTT 的平均绝对变化、路径模式和样本年龄。
探测在十秒期限到达后才记为未响应；等待中的探测和 ICMP 补充测量不计入丢失率。
测量路径或对端代次改变时清空窗口。年龄使用本地单调时钟，收到报告后保守地
加上此次查询的往返耗时，不比较两台电脑的系统时间。

**丢失率表示探测往返未响应比例，不代表单向丢包或游戏数据丢包。**
超过 15 秒的数据
视为过期；少于五个已完成样本会提示证据不足。候选的两段均须有原生直连状态。
可用候选优先按样本充分程度排序，再比较估计组合探测丢失率和两段 RTT 之和。
组合丢失率估计假设两段丢失相互独立，只用于辅助排序，最终由用户选择。

## 授权与切换

控制消息复用现有虚拟网络发现通道，核对已知发送者和 T/R/L 三方身份。
R 对每份申请明确同意，先安装转发会话，再让 T、L 安装仅接收和探测的准备状态。
收到两端确认后，才提交发送路径切换。重发不会重复创建会话；建立失败或取消
会撤销配置，近期关闭的会话 ID 会短暂保留，拒绝延迟到达的建立消息。

原生通过 `get_info.peer_assist_version = 1` 广告能力。
`set_peer_assist` 参数为 `[circuit, role, first_mac, second_mac, enabled]`，
其中 `circuit` 为 32 位十六进制 ID。`relay` 的两个 MAC 分别为 T、L；
`standby` 和 `endpoint` 的两个 MAC 分别为通信对端、R。
`standby` 允许接收和探测，但不改变游戏数据发送路径。
`get_peer_assists` 返回已安装角色、实际就绪状态和包计数。

原生配置 30 秒未续期失效。R 每三秒发送控制保活，并要求两端回应；端点只在
收到 R 的保活后续期。控制通道静默 15 秒会结束协助。另有原生探测实际经过 R
到达通信对端，维护六秒的数据路径就绪租约。路径未就绪时沿用现有传输选择；
不会擅自改用另一位玩家。

## 数据路径

原生 edge 在原始 n3n 数据包外增加 44 字节协助封装。每一段使用已验证的 IPv6
或已建立的 IPv4 直连，包括打洞胜出的工作 socket。R 不会经 supernode 或其他
协助会话递归转发，也不会将过路数据写入自己的 TAP 网卡。
接收时核对源、目标、会话、直接发送者和跳数标志，并用有界序号窗口去除重复
协助数据报。端点仍执行 n3n 的社区、头部、时间戳和负载解码检查，不会将 R 的
socket 学成原始发送者的直连地址。

IPv6 段复用现有尺寸发现与分片，计算尺寸时包含新增封装。IPv4 段沿用原有 IPv4
报文处理。加封装后超过原生缓冲区的内层报文使用原路径。每个数据报走一条
选定路径，传输层不重传。原先可用的 IPv4 直连会保活；手动强制服务器中继优先。
广播发现保持原路径，虚拟 IP、MAC 和游戏 socket 不变。

R 转发两个方向的数据，会同时占用上传和下载。首版没有用户带宽限额或自动容量
预留；R 可以拒绝或结束具体会话。持有小组共享密钥的 R 能够解密这些流量。

## 协助链路故障诊断

原生 edge 将 `MikuN2N assistdiag` 和 `MikuN2N v6peer` 摘要写入普通本地日志，
无需开启额外的 IPv6 详细跟踪。计数有变化时约每十秒输出一次；会话移除和对端或
路径重置前保留累计计数。不记录游戏载荷或会话密钥。这些记录沿用现有诊断采集
与上传授权。

`assistdiag` 带本机 MAC、会话、角色、创建时间、单调采样时间和原始源/目标 MAC。
T、R、L 对同一方向使用相同的源/目标标识，DATA 与 PING/PONG 分开计数。
记录发送尝试、提交 UDP、收到封装、通过封装校验、内层 n3n 校验和写入 TAP 的阶段。
`tx_consumed_drop` 表示现有传输逻辑已消费数据包，但未成功提交全部 UDP 分片。
拒绝原因区分端点/跳数、就绪状态、序号、内层头部/社区/身份、变换、过滤和 TAP 错误。
端点的 `tx_failed` 可以回退普通路径；R 转发失败则没有这一回退。
payload 计数覆盖不支持的压缩类型。

`get_peer_assists` 通过 `diagnostics_version = 1` 返回同一组双向累计计数。
存在本地协助电路时，客户端查询管理接口，约每 10–12 秒及观察到状态变化时记录
`management_peer_assists`，附会话到三方身份的映射。失败查询沿用相同的记录节奏，
记录 `success=false`、错误类型和 null rows，与查询成功但表为空区分。
维护轮次开始时若没有本地电路，会跳过查询和快照。快照通过会话的诊断记录器写入，
前提是该记录器可用；因大小限制截断时有明确标记。
`peer_assist_control` / `MikuN2N assistctl` 以同一会话标识串起建立、原生配置、
就绪状态变化、超时和移除。

IPv6 计数按直接相邻的外层对端划分，包含该段全部流量，也包含 R 自己的流量。
区分数据报、UDP 分片、成功或不完整提交、重组完成、槽占用与峰值、槽满丢弃、
重组过期及缺失字节、重复、冲突重叠和已退役/窗口拒绝。四个槽、两秒超时的
策略保持不变。过期仍按原逻辑惰性清理：槽过期后可能暂未释放，直到下一个分片
触发清理；摘要区分这类槽与尚未过期的占用。重置前记录尚未完成的重组。
IPv6 的 `gen`、`path_gen`、`seq` 仅在本机有效；分片 ID 属于发送端整个会话，跨对端
分配，未分片 DATA 没有分片 ID，不能用按对端看到的 ID 空洞推算丢包。
`delivered` 仅表示 IPv6 解封装返回完整数据报，后面仍有协助/n3n 校验和 TAP 写入。
内容相同的重复、可接受的重叠和等待后续分片本身不算丢弃。过短或未知会话的协助包
无法归属到某个会话；错误 IPv6 头也只有能确认已知端点时才归属计数，这类无法
归属的流量不包含在各会话总量中。

排查超时时，保留 T/R/L 从建立协助前到超时、结束后的完整日志，以及 MC 服务端
的断开原因。按同一会话、同一方向逐段比较：

1. 对比 T 提交的 DATA 与 R 收到/校验的 DATA，再比较 R 提交的 DATA 与 L 收到/
   校验的 DATA；反方向同样处理。
2. 收到阶段有缺口时，比较直接相邻两端的 IPv6 分片计数和重组拒绝原因。
   槽满丢弃增长可直接证明本地发生过槽耗尽。
3. 终点通过封装校验后，继续看内层校验与 TAP 写入，区分原生处理丢弃和封装
   抵达之前的缺口。

UDP 提交计数表示本机 socket 接受的数据报数量，后续交付情况看下一台机器的
接收计数；写入 TAP 之后的处理查游戏日志。不同电脑的时钟没有同步，应按会话、
方向和序号比较完整且重叠的观察窗口。在途包、重复包、重置、日志缺失和并发
采样都会影响计数差，应结合各阶段的拒绝原因比较。序号最高值标识已观察到的
最大序号，具体缺包需要逐包记录。

## 实机验证

游戏验收使用三台参与测试的机器和匹配版本，测试加载世界、线路切换、
协助者退出或撤销及恢复过程，同时观察 R 自己的游戏和浅深两套主题。
记录实际承载路径、连续卡顿和服务器中继流量。这些实测也用于评估小型质量
探测未覆盖的带宽和大报文表现。
