## 排查结论（26-07-25）

### 事实对照

| | 我方 (192.0.2.45) | 对方 ADMIN (192.0.2.163) |
|---|---|---|
| n3n NAT 探测 | NAT4，映射/过滤均 addr-and-port-dependent，external `198.51.100.139:26796/25859`（探测于 20:49:40） | NAT4，映射/过滤均 addr-and-port-dependent，external `198.51.100.101:34848/34856`（探测于 21:32:10） |
| natpunch 实测 | mode=sym conf=82%，banks=[26091,26856]，control 映射 26807 | **mode=cone conf=100%，reuse=25/25，banks=[35843,35843]** |
| n3n 角色 | anchor（base=34848，21 个固定目标 ±256） | scanner（base=27096，近窗 ±1..64 + 轮转带 ±65..4288） |
| n3n 结果 | 22s / 2898 包耗尽，pSp | 22s / 9108 包耗尽，pSp |
| natpunch 结果 | 438ms 打通，真实端点 `198.51.100.101:35886` | 375ms 打通，真实端点 `198.51.100.139:27089` |

natpunch 的命中细节是全部线索的关键：对端在 **我方 bank2=26856 之上 +233**（`predicted=222`，固定覆盖 `banks+1..256`）打中了 `27089`；而我方 natpunch 的 control 映射是 26807。也就是说，**真正能打通的端口和"supernode 观测到的 control 端口"没有固定关系，它取决于当前那一刻的 NAT 计数器（bank）值。**

### 根因（按置信度排序）

**1. n3n 的搜索基准选错了，而且这个信息根本没有交换机制（主因）**

`mikun2n_punch_peer()` 里 `base = pp->sock.port`——即 supernode 观测到的对端 control 端口——然后在 `base ± offset` 上搜索。对**对称 NAT** 而言这个基准是错的：

- supernode 映射是**会话建立那一刻**分配的（我方 20:49:37），而打洞映射是**打洞那一刻**新分配的（21:32:08），中间隔了 43 分钟的计数器漂移；
- 更根本的是，addr-and-port-dependent 映射对每个目的地各分配一个端口，supernode 映射（→3076）和打洞映射（→对端 IP）之间的差值是**无界的**。日志里我方对 21001/21002/3076 三个目的地就拿到 26796/25859/27096 三个互不相干的值（其中两个相差 937＝双活网关的两 bank 间隔）。

natpunch 之所以 400ms 就赢，是因为 v6 起它通过服务器交换了 `BANKS room sp cb1 cb2`：**打洞 socket 的固定端口 + 当前计数器两个 bank**，对端直接往 `bank+1..256` 撒。n3n 补丁里**完全没有这套交换**——我 grep 过 `src/`，没有任何 bank/counter 字段进入 REGISTER 或 supernode 转发。`get_nat` 明明同时测到了两个 bank（26796/25859），但只报给本机 UI，从不告诉对端。

**这等于 n3n 现在停留在 natpunch v5 的设计上**，而 v5 在记忆里已经被判定为死锁（见 memory `nat-p2p-breakthrough` 的 v5→v6 段落）。

**2. 端口受限过滤 × 21 个 anchor 映射 = 只有 1 个目标是有效的**

我方过滤是 address-and-port-dependent。anchor 向 `34848 ± {0,±1,±2,±4,…,±256}` 共 21 个目的端口发包，对称 NAT 会为这 21 个目的地各开一个**不同外部端口**的映射。而对端（cone）回喷时源端口只有一个（34848）。所以我方 21 个映射里，**只有 offset=0 那一个**（对 34848 建的）会放行对端的包，其余 20 个是纯浪费，而且第一 tick 建它们时还额外推高了自己的计数器。

对端要成功，必须恰好命中这**唯一一个**端口，而它连这个端口在哪个区间都不知道（见根因 1）。

**3. 全范围扫过一遍仍未命中：单发覆盖、无重打**

> 修正（复核后）：初稿写的"两边起跑差 4 秒、重叠只有 18 秒"是**错的**，那是时钟偏差造成的假象。用 natpunch 的配对事件对表（服务器同一瞬发 PAIR，rtt=23ms）：我方记 `21:36:12.849`，对端记 `21:36:16.500` → **对端系统时钟快约 3.65 秒**。换算回 n3n：对端 21:32:12.241（其钟）= 我方钟 21:32:08.59，我方 21:32:08.260 起跑——**真实世界只差 0.3 秒，22 秒预算几乎完全重叠**。

对账对端 scanner 的发包量：每 tick `4(control) + 32(近窗) + 96(带) + 1(drift) = 133` 包，4 tick/s，22s 理论 ~11700；实际 9108，恰好等于候选总数 `64×2 + 4224×2 = 8576` 加上 control 重发。**也就是说它把 `27096 ± 1..4288` 完整扫了一遍，每个候选恰好一发，然后就耗尽了。**

于是真正的问题不是"没扫到"，而是：

- **每个候选只有一发，丢包即永久烧掉该候选**，没有任何重打。natpunch 相反——每个 GO 轮都重新撒最高概率区间（`banks+1..256` + `predicted`）。
- 以 ~532 pps 向单一 IP 的上千个端口发包，行为特征等同端口扫描，被两侧 CGNAT 限速/丢弃很可能（此条为假设，日志无法证实）。

**而且全范围扫过一遍都没中，反过来强化了根因 1**：我方对着对端 IP 的那个映射端口很可能根本不在 `27096 ± 4288` 内——而 n3n 既无从知道它在哪，也从不把自己的值告诉对端。

**3b. "共享墙钟时隙"同步机制被时钟偏差静默破坏（潜在 bug）**

`round = (now_ms/250/4) % 22`、`phase = common_slot % 4` 全部取自各自的 OS 墙钟，源码注释明写依赖它来"even when peers enter Tier 1 at different times"。实测对端时钟偏 **3.65 秒 = 14.6 个 250ms slot / 3.65 个 band**——两边算出的 band 和 phase 根本不是同一个。

本次没有因此炸掉，只是因为我方恰好是 anchor（不使用 round）。换成 scanner↔scanner 或 layered 角色就会直接错位。**不能依赖端侧墙钟做同步，必须由 supernode 授时。**

**4. 对端 NAT 被误判为 NAT4，导致进了最硬的 NAT4↔NAT4 策略**

两个工具跑的其实是**同一个测试**（同一服务器 IP `vps.example.com` 的 21001/21002 两个端口，看同一 socket 的外部端口是否相同），只是样本量差 25 倍：

| | 样本 | 观测 | 判定 |
|---|---|---|---|
| natpunch (`natpunch.c:403`) | 25 socket × 2 目的端口 = 50 | 全部 `mapped_a == mapped_b` → `reuse=25/25` | cone，conf=100% |
| n3n | 1 socket（数据 socket）× 2 目的端口 = 2 | 34848 / **34856**（差 8） | addr-and-port-dependent |

n3n 还漏掉了自己手上的第三个观测点：supernode 看到对端注册端口同样是 **34848**（我方日志 `punch started for peer port 34848`）。同一 socket → 三个目的端口（3076/21001/21002）→ `34848 / 34848 / 34856`，**三分之二一致**。

`+8` 的具体成因从日志定不下来（对端 CGNAT 多引擎？单发探测异常？），但成因不重要——**问题在于分类器是零容忍的：只要 A≠B 就直接归到最坏一类**，一个异常样本就能把 cone 翻成对称。2 个样本本就不足以做这个判定。

判定边界（需诚实标注）：两个工具都只用**一个服务器 IP**，所以测到的严格来说只是"映射与**目的端口**无关"，**未测"与目的 IP 无关"**；对端理论上仍可能是 address-dependent。但从打洞结果看，我方按对端 control 端口 35843 撒 `±1..64` 就命中了它 worker#17 的 35886，实践上按 cone 打是成立的。

**ADMIN 实际是锥形**。如果 n3n 知道这一点，这就是已经验证可行的 NAT3↔NAT4 场景（记忆里橙梦那类），正确打法是我方只对它那一个固定端口建**唯一一个**稳定映射，而不是撒 21 个。现在两边都自报 NAT4 → 双方按 MAC 分 scanner/anchor → 用最难的策略打一个本来不难的组合。

另外 NAT 探测只在启动时做一次（20:49），21:32 打洞时用的是 43 分钟前的旧判定，期间从未复测。

正确配对是 **s3 会话**（`n2n-20260725-213641-646-s3.log`，0.5.1）而非文档里贴的 s5（0.4.1，22:10 启动、与对方不同时）：

- 日志中 phase-0 行缺失 round **3、4、6、12、14** ——丢 tick 造成的**空洞**的直接可见证据，说明截断不是发生在末尾而是中间挖洞；

### 建议的修法（按性价比）

1. **把 bank 信息搬进 n3n**（对应 natpunch v6 的突破点）。`get_nat` 已经有测量能力，需要的是：打洞前**即时**复测两个 bank，把 `(sp, cb1, cb2)` 通过 supernode 转发给对端（REGISTER_SUPER 扩展字段或新管理消息），对端把 `base` 从 `pp->sock.port` 换成 `cb1/cb2`，并**只向上撒 `+1..256`**（计数器单调递增），而不是 `±`。这是唯一能真正解决根因 1 的改动，其余都是缓解。
2. **交换 NAT 类型并按组合选策略**。对端是 cone 时：我方只对它的单一端口建一个映射（anchor 退化成 1 个目标），把发包预算全给"保活 + 让对端扫"；scanner 侧则享受"目标只有一个稳定端口"。顺带修正探测器：两个样本不足以判对称，至少要多目的地/多 socket 采样，或直接采信 `reuse` 语义。
3. **同步改由 supernode 授时，并放弃"扫一遍"式覆盖**。supernode 是天然会合点，让它下发共同的开火时刻和轮次编号，取代现在取自各端 OS 墙钟的 `common_slot`（实测偏差 3.65s，见 3b）。同时把等概率轮转带改成"每轮重打高概率区间"，别再让每个候选只有一发。
4. **anchor 停止多目标撒点**。它现在既污染自己的计数器，又制造 20 个永远不会被使用的映射。
5. **修 NAT 分类器**。至少多 socket / 多目的地采样并引入多数表决，别让单个异常样本把 cone 判成对称；把 supernode 观测到的注册端口也作为一个样本纳入。有条件的话给探测服务器加第二个 IP，才能真正区分 port-dependent 和 address-dependent。
